# 10 — แผนไปให้ถึง PPL ≈ 5

## ความจริงข้อแรกที่ต้องเข้าใจก่อน

> **PPL ไม่ได้ขึ้นกับโมเดลอย่างเดียว — ขึ้นกับ *ข้อความที่เอามาวัด* ด้วย**

ตัวเลข "PPL 5" จึงไม่มีความหมายจนกว่าจะระบุว่าวัดบนอะไร
ข้อความคนละประเภทมี **entropy** ต่างกันโดยธรรมชาติ และไม่มีโมเดลใดเอาชนะ entropy ของข้อความได้

| ประเภทข้อความ | PPL ที่โมเดลดี ๆ ทำได้ | ทำไม |
|---|---|---|
| ข้อความซ้ำซาก (เมนู เทมเพลต) | 2–4 | คาดเดาได้เกือบหมด |
| **สารานุกรม / Wikipedia** | **4–7** | โครงประโยคซ้ำ ๆ ศัพท์วนเวียน |
| ข่าว / บทความทั่วไป | 6–10 | |
| **ร้อยแก้วเชิงวรรณกรรมหนาแน่น** | **9–15** | ข้อมูลใหม่ทุกประโยค ศัพท์เฉพาะเยอะ |
| บทกวี / ข้อความสร้างสรรค์ | 15–40 | |

**บทที่เขียนเองใน `data/raw/ch*.md` อยู่แถวล่างของตาราง** — เป็นร้อยแก้วหนาแน่นที่ตั้งใจให้มี
ประโยคยาว 35–60 คำ ศัพท์เทคนิค ชื่อนักวิจัย และตัวเลขปีเต็มไปหมด
ซึ่งเป็น *เป้าหมายของโปรเจกต์* แต่ก็เป็นข้อความที่ PPL ต่ำได้ยากที่สุดประเภทหนึ่ง

**ดังนั้น PPL 5 บนบทหนังสือคือเป้าที่แทบเป็นไปไม่ได้** ส่วน PPL 5 บนคลัง Wikipedia
สายวิทยาศาสตร์นั้น **เป็นไปได้จริง** และเป็นเส้นทางที่แผนนี้เลือก

## เส้นทางที่เลือก

### สิ่งที่เปลี่ยนไปจากรันแรก

| | รันแรก (smoke test) | รันนี้ |
|---|---|---|
| คลัง train | 15 บล็อก (16K token) | **~15,000 บล็อก (~15.5M token)** |
| แหล่งข้อมูล | หนังสือ 8 บท | หนังสือ 8 บท + **Thai Wikipedia สายวิทย์ 8,127 บทความ** |
| val | **1 บล็อก** | ~300 บล็อก |
| lora_r | 16 | **64** |
| optimizer step | 8 | **~2,000 ต่อ epoch** |
| เวลา | 2 นาที | **~1 วันต่อ epoch** |

คลังใหญ่ขึ้นเกือบ **1,000 เท่า** ซึ่งเป็นตัวแปรที่สำคัญที่สุด
เพราะรันแรกไม่ได้ล้มเหลวเพราะ hyperparameter ผิด แต่ล้มเหลวเพราะ **ไม่มีข้อมูลให้เรียน**

### วิธีคัดคลังโดเมน

`src/build_corpus.py` สตรีม Thai Wikipedia ทั้ง 159,719 บทความ แล้วให้คะแนนความหนาแน่นของคำสำคัญ

| กลุ่มคำ | น้ำหนัก | ตัวอย่าง |
|---|---|---|
| เฉพาะทางแคบ | 3 | เซลล์ประสาท · ไซแนปส์ · โดพามีน · ฮิปโปแคมปัส · ไมอีลิน |
| กลาง | 2 | สมอง · ฮอร์โมน · พฤติกรรม · สรีรวิทยา · การทดลอง |
| กว้าง | 1 | เซลล์ · โปรตีน · ยีน · โรค · สุขภาพ |

เก็บเฉพาะบทความที่ได้คะแนน ≥ 3 และยาว ≥ 1,200 อักขระหลังทำความสะอาด

**การทำความสะอาดสำคัญพอ ๆ กับการคัดเลือก** — ตัดส่วนอ้างอิง ดูเพิ่ม ระเบียงภาพ
และตัดบรรทัดที่เป็นรายการ ตาราง หรือสั้นกว่า 120 อักขระออกทั้งหมด
เพื่อให้เหลือเฉพาะย่อหน้าร้อยแก้ว ซึ่งตรงกับกฎใน [book/STYLE_GUIDE.md](../book/STYLE_GUIDE.md)

## ทำไมถึงคาดว่าจะถึง 5 ได้

การลด PPL ด้วย CPT มาจากสามกลไกที่บวกกัน

**1. โมเดลเรียนคำศัพท์เฉพาะทางที่เคยเจอน้อย**
คำอย่าง "ไซแนปส์" "ฮิปโปแคมปัส" "ออลิโกเดนโดรไซต์" อยู่ท้าย ๆ ของการกระจายที่ typhoon-7b เคยเห็น
เมื่อเจอซ้ำหลายพันครั้ง ความน่าจะเป็นที่โมเดลให้กับคำเหล่านี้จะสูงขึ้นมาก

**2. โมเดลเรียนโครงประโยคของสารานุกรมไทย**
Wikipedia มีรูปแบบซ้ำสูงมาก — "X เป็น Y ที่..." "ค้นพบโดย... ในปี..." "แบ่งออกเป็น... ประเภท"
รูปแบบพวกนี้เรียนได้เร็วและให้ผลลด PPL แรงที่สุด

**3. โมเดลเรียนความสัมพันธ์ระหว่างแนวคิดในโดเมน**
เมื่อเห็น "ไมอีลิน" โมเดลจะเริ่มคาดว่า "แอกซอน" "การนำสัญญาณ" "ปลอกหุ้ม" น่าจะตามมา

กลไก 1 และ 2 ให้ผลเร็ว (เห็นได้ใน 1 epoch แรก) ส่วนกลไก 3 ต้องใช้เวลานานกว่า

---

## ตารางเวลาโดยประมาณ

วัดจาก throughput จริงบน RTX 4060 8GB: **~17 วินาที/step ที่ grad_accum=4**

| ขั้น | จำนวน step | เวลาโดยประมาณ |
|---|---|---|
| epoch 1 | ~1,900 | ~18 ชม. |
| epoch 2 | ~1,900 | ~18 ชม. |
| epoch 3 | ~1,900 | ~18 ชม. |
| **รวม 3 epoch** | **~5,700** | **~2.3 วัน** |

อยู่ในงบเวลา 5–10 วันที่ตั้งไว้ และยังเหลือที่ให้รันเพิ่มถ้า PPL ยังไม่ถึงเป้า

**checkpoint ทุก 1,000 step** (~5 ชม.) → ไฟดับหรือเครื่องรีสตาร์ทก็กู้คืนได้

---

## จุดที่ต้องเฝ้าระวังระหว่างรัน

| สัญญาณ | หมายความว่า | ทำอย่างไร |
|---|---|---|
| `eval_loss` นิ่งตั้งแต่ step 500 | lr ต่ำเกินหรือ `lora_r` ไม่พอ | เพิ่ม lr หรือ r แล้วรันใหม่ |
| `eval_loss` ลงแล้วเด้งขึ้น | เริ่ม overfit | หยุดที่ checkpoint ก่อนหน้า |
| `train_loss` ต่ำกว่า `eval_loss` มาก | ท่องจำ | ลด epochs |
| **general PPL พุ่ง** | catastrophic forgetting | เพิ่ม `replay_ratio` |
| VRAM ใกล้ 8 GB | เสี่ยง OOM กลางคืน | ลด `lora_r` เหลือ 32 |

## ถ้ายังไม่ถึง 5 หลังจากนี้

เรียงตามผลตอบแทนต่อความพยายาม

| # | ทำอะไร | ผลที่คาด |
|---|---|---|
| 1 | รันเพิ่มอีก 2–3 epoch | −0.3 ถึง −0.8 |
| 2 | เพิ่ม `lora_r` เป็น 128 (ถ้า VRAM ไหว) | −0.2 ถึง −0.5 |
| 3 | เติมคลังจาก `HuggingFaceFW/fineweb-2` config `tha_Thai` (คลังเว็บไทยขนาดพันล้าน token) | −0.5 ถึง −1.5 |
| 4 | เพิ่ม `seq_len` เป็น 2048 (context ยาวขึ้น = ทำนายง่ายขึ้น) | −0.3 ถึง −0.7 |
| 5 | ทำ full fine-tuning แทน LoRA | −1.0 ขึ้นไป แต่ **ต้องการ VRAM 116 GB** — ทำบนเครื่องนี้ไม่ได้ |

ข้อ 3 คือทางที่เหลือมากที่สุด เพราะ Thai Wikipedia หมดแล้วที่ 15.5M token
ในขณะที่ fineweb-2 ภาษาไทยมีข้อมูลมากกว่านั้นหลายสิบเท่า

## สิ่งที่ต้องรายงานเมื่อจบ

ไม่ว่าจะถึง 5 หรือไม่ ต้องรายงานทั้งสามตัวเลขคู่กันเสมอ

```
domain PPL   (Wikipedia สายวิทย์ held-out)   ← เป้าหมาย ≈ 5
book PPL     (บทหนังสือ held-out)            ← เป้าหมายรอง คาดว่าจะสูงกว่ามาก
general PPL  (Wikipedia ทั่วไป held-out)     ← ต้องไม่พุ่ง = ไม่ลืมของเดิม
```

**และต้องรัน `python main.py probe` ทุกครั้ง** เพราะ PPL ต่ำไม่ได้แปลว่าโมเดลไม่หลอน
รันแรกพิสูจน์แล้วว่า PPL ดีขึ้นได้พร้อมกับที่โมเดลแต่งชื่องานวิจัยขึ้นมาเอง
(ดู [RESULTS.md §6.5](../RESULTS.md))
